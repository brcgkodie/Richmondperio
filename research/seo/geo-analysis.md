## 2. AI Crawler Access Status

### robots.txt

**Old site** (`https://www.richmondperioonline.com/robots.txt`):
```
User-agent: *
Disallow: /wp-admin/
Allow: /wp-admin/admin-ajax.php
Sitemap: https://richmondperioonline.com/sitemap_index.xml
```

**New site** (`https://richmondperio.vercel.app/robots.txt`, generated by `app/robots.ts`):
```
User-Agent: *
Allow: /
Sitemap: https://richmondperio.com/sitemap.xml
```

Neither site has bot-specific rules — both use a wildcard `User-agent: *` block, which allows all AI crawlers by default. Live-fetch tests confirmed 200 OK responses (no bot-specific blocking, no `X-Robots-Tag` header, no WAF challenge observed) for:

| Crawler | Old site | New site |
|---|---|---|
| GPTBot | Allowed (200) | Allowed (200) |
| ClaudeBot | Allowed (200) | Allowed (200) |
| PerplexityBot | Allowed (200) | Allowed (200) |
| OAI-SearchBot | Allowed (wildcard) | Allowed (wildcard) |
| Google-Extended | Allowed (wildcard) | Allowed (wildcard) |
| CCBot / anthropic-ai | Allowed (wildcard, not split out) | Allowed (wildcard, not split out) |

**Finding**: Neither site currently distinguishes "AI search" crawlers (GPTBot, OAI-SearchBot, ClaudeBot, PerplexityBot — wanted for citation visibility) from "AI training only" crawlers (CCBot, anthropic-ai, Google-Extended-for-training) — everything is allowed under one wildcard rule. This is safe for citation visibility (nothing is blocked) but leaves no explicit policy on the training-data question, which some practices choose to control separately. Recommend adding named allow rules for the four priority crawlers regardless, so intent is explicit and auditable rather than implicit via wildcard.

**Note**: this curl-based test cannot detect crawler-specific behavior gated on IP-range verification (e.g., a bot-management layer like Cloudflare that only challenges verified bot IP ranges). Vercel/Apache showed no such layer active, but this should be spot-checked again after the new site's DNS/hosting is finalized.

## 3. Content Citability

### Old site (richmondperioonline.com)

- **No per-procedure pages.** All 6 procedures (dental implants, gum grafting, bone grafting, crown lengthening, periodontal disease treatment, extractions) are combined into a single page, `/dental-services/` (916 visible words across all six topics — roughly 150 words per procedure).
- **No FAQ content or FAQ schema anywhere on the site.**
- **No direct answers to citation-worthy queries.** Checked specifically for "what does a periodontist do," "how much does gum grafting cost," "dental implant recovery time" — none are answered as a self-contained passage. Gum grafting is described narratively ("A gum graft will protect your teeth from any damaging effects of gum recession...") with no recovery-time figure, no cost figure, no numbered answer block.
- **Structured data is generic WordPress/Yoast output**: `WebPage`, `WebSite`, `BreadcrumbList`, `SearchAction` only. No `MedicalClinic`/`Dentist`, no `Physician`, no `FAQPage`, no `MedicalProcedure`.
- Site sitemap (`page-sitemap.xml`) lists only **16 URLs total** — no blog, no reviews page, no results/before-after page, no patient-resources content is indexed as separate pages.

**Net effect**: an AI answer engine crawling this site has almost nothing extractable as a clean, quotable, source-attributed passage for any of the target queries. The content exists but is buried in one long undifferentiated page with no schema signal to help a model identify it as an authoritative answer.

### New site (richmondperio.vercel.app / "Grove Periodontists")

Substantially better structure:

- **6 dedicated procedure URLs**, each with 3–4 topic sections (~90–120 words each) plus a benefits list plus an FAQ block — e.g. `/services/dental-implants`, `/services/gum-grafting`, `/services/bone-grafting`, `/services/crown-lengthening`, `/services/periodontal-disease-treatment`, `/services/tooth-extractions`.
- **FAQPage schema present and valid on all 6 procedure pages** (8–12 Q&A pairs each), covering exactly the query types requested:
  - "How much do dental implants cost?" ✅ present, but answer is non-numeric ("varies... we provide detailed cost estimates during your consultation") — **this will not satisfy or get cited for the literal "how much does X cost" query**, which AI Overviews/Perplexity strongly prefer to answer with a number or range.
  - "How long does recovery from gum grafting take?" ✅ present with specific figures ("1 to 2 weeks" initial healing, "2 to 3 months" full maturation) — good citability.
  - "What does a periodontist do?" — **not directly answered anywhere on the site** (closest is "Why Choose a Periodontist for Dental Implants?" on the implants page, which answers a narrower question). This is a foundational entity-definition query and should get its own answer block.
- **FAQ answer length**: measured 35–53 words per answer across all 6 pages (avg. ~45 words). This is well-suited to being lifted whole into a featured-snippet/AI-Overview card, but shorter than the 134–167-word "optimal passage" range cited for body-content citation — the FAQ layer is doing snippet-length work; the body **section** paragraphs (90–120 words) are closer to optimal length and should be tightened toward the 134–167w band rather than shortened further.
- Section headings are already question-phrased in several places ("What Are Dental Implants?", "Why Is Bone Grafting Necessary?", "What Is Crown Lengthening?") — good pattern, not yet applied consistently to all H2s (some are noun-phrase headings like "Types of Dental Implants We Offer").
- Blog exists with 3 posts (`/blog/what-to-expect-dental-implant-consultation`, `/blog/signs-of-gum-disease-and-when-to-see-periodontist`, `/blog/gum-grafting-recovery-tips`) — good topical coverage, but posts carry no `FAQPage`/`Article`/`BlogPosting` schema (only the sitewide `MedicalClinic`/`BreadcrumbList` schema), and no visible byline/author.
- **No dedicated `/faq` hub page** — FAQs exist only embedded per-service; a consolidated FAQ page (with its own broader `FAQPage` schema covering practice-level questions like insurance, sedation, "what does a periodontist do," "periodontist vs. dentist") is missing.
- **No cost/recovery comparison table anywhere on the site.** This is the single biggest citability gap relative to how Google AI Overviews and Perplexity like to surface medical/cost content (they favor scannable tables over prose for "how much does X cost" and "how long is recovery" query classes).

**Technical bug found in source**: duplicate `FAQPage` JSON-LD is emitted on every procedure page. `components/services/FAQAccordion.tsx` renders `<FAQSchema faqs={faqs} />` (which itself calls `generateFAQSchema()` from `lib/schema.ts`), **and** `app/services/[slug]/page.tsx` (lines 468–485) separately injects an identical inline `<script type="application/ld+json">` block with the same `FAQPage` data. Verified via raw HTML: 2 identical `FAQPage` blocks per procedure page. This isn't fatal to citation, but it's redundant, will generate duplicate-markup warnings in Google Rich Results Test, and should be fixed by removing the inline block in `page.tsx` and keeping only the `FAQSchema` component.

### Structured data comparison

| `MedicalClinic` (practice entity) | No | **Yes** — sitewide, all pages |

| `sameAs` (social entity links) | No | Yes, but see issue below |

### Entity-consistency issue (new site)

The new site's `MedicalClinic` schema (`lib/schema.ts`) declares `sameAs` links to:
```
https://www.instagram.com/owdperio/
https://www.facebook.com/owdperio
```
These are the **old brand's** handles ("OWD" = Overstreet, White & Dunegan) while the new site's `name` field and all on-page copy present the practice as **"Grove Periodontists."** When AI models and Google's Knowledge Graph try to resolve the entity behind richmondperio.com, a name mismatch between the site's own brand and its declared `sameAs` social profiles is a real disambiguation risk — it either dilutes both entities or causes the model to treat them as unrelated, undermining exactly the kind of authority signal `sameAs` exists to provide. This needs a decision before launch: either the social accounts get rebranded to Grove Periodontists (and schema stays as-is), or new "Grove Periodontists" profiles are created and schema is updated to point to those instead — do not launch with mismatched entity names in production schema.

### Brand mention presence (external)

Checked both site's on-page links and could not verify live third-party presence via crawl (that requires a search/social API, not just fetching these two URLs) — flagging as **unverified, needs manual/API check** rather than guessing:

| Signal | Status found in on-page links | Correlation w/ AI citation |
|---|---|---|
| YouTube | **Not linked from either site** — no channel referenced | ~0.737 (strongest signal) |
| Reddit | Not referenced on either site | High |
| Wikipedia | Not referenced (expected — unlikely for a private practice) | High |
| LinkedIn | Not referenced on either site | Moderate |
| Yelp / Healthgrides / Google Business Profile | Not linked in schema `sameAs` on either site | Moderate |

**This is the largest authority gap on both sites.** Given YouTube has the single strongest measured correlation with AI citation (0.737) and neither site links to or appears to have a YouTube presence, this is a genuine opportunity, not just a checklist item — see Action Plan §5.

## 5. Technical Accessibility

- **Both sites are server-rendered** (WordPress/Apache on old; Next.js SSR/SSG on new) — confirmed by plain `curl` (no headless browser) returning full HTML content on every page tested. This means CSR-blocking is **not** an issue for either site; AI crawlers that don't execute JavaScript can still read full content on both.
- **Critical bug — domain/canonical mismatch on the new site.** Direct read of the rebuild's source confirms three different domains are referenced across the codebase for what should be one canonical production URL:
  - `app/layout.tsx` → `metadataBase: new URL("https://richmondperioonline.com")`, `openGraph.url: "https://richmondperioonline.com"`, `alternates.canonical: "https://richmondperioonline.com"` — **points at the OLD site's domain**
  - `app/sitemap.ts` → `const BASE_URL = "https://richmondperioonline.com"` — every URL in the generated sitemap.xml resolves to the old domain (confirmed live: `curl https://richmondperio.vercel.app/sitemap.xml` returns `<loc>https://richmondperioonline.com/...</loc>` for all 33 URLs)
  - `app/robots.ts` → `sitemap: "https://richmondperio.com/sitemap.xml"` — points at a **third** domain (no `www`, `.com` not `online.com`)
  - `lib/constants.ts` → `SITE_URL = "https://richmondperioonline.com"`, `PRACTICE_EMAIL = "info@richmondperioonline.com"`
  - Team and blog pages hardcode `https://richmondperioonline.com/...` in breadcrumb schema (`app/team/[slug]/page.tsx`, `app/blog/[slug]/page.tsx`)

  **Impact**: if the rebuild launches on its intended production domain (`richmondperio.com` per `app/robots.ts`, or `richmondperioonline.com` if it's replacing the old site in place) without fixing these, canonical tags, Open Graph URLs, sitemap URLs, and breadcrumb schema will all point to a domain that either isn't the live one or is still serving the old WordPress site. This will actively work against citation — Google/AI crawlers may treat the new content as a duplicate of, or subordinate to, whatever's actually living at richmondperioonline.com, and any citation credit will attribute to the wrong URL. **This is the single highest-priority fix before launch**, ahead of any content work.

- Sitemap on new site is broader and more complete than old (33 URLs incl. all 6 services, 4 team pages, 2 locations, 3 blog posts, patient resources) vs. old site's 16 URLs with no procedure-level pages.
- No `X-Robots-Tag` blocking headers on either site; no bot-specific 403/429s observed for GPTBot/ClaudeBot/PerplexityBot user agents.
- No RSL 1.0 licensing markup on either site.

## 6. GEO Action Plan for the New Site (richmondperio.vercel.app / Grove Periodontists)

### A. Content structures to add

1. **Cost/recovery reference table per procedure page** — a simple scannable HTML table (not just prose) directly under each procedure's intro, e.g.:

   | Procedure | Typical Cost Range* | Recovery Time | Full Healing |
   |---|---|---|---|
   | Single dental implant | $X,XXX–$X,XXX | 3–5 days initial | 3–6 months (osseointegration) |
   | Gum grafting (per site) | $XXX–$X,XXX | 1–2 weeks initial | 2–3 months |
   | Bone grafting | $XXX–$X,XXX | 3–7 days initial | 4–6 months |

   *Needs real numbers from the client — current FAQ answers dodge the cost question entirely ("varies... consultation"), which is the single most-searched query type this practice will lose citations on. Even a wide range ("$3,000–$6,000 per implant, before insurance") is dramatically more citable than "varies." Tables also directly address the "Multi-Modal Content" scoring gap (currently 40/100 on new site).

2. **Answer-first opening paragraph on every procedure page** — lead with a 40–60 word direct answer to the page's core question before any marketing copy, e.g. dental implants page should open: "A dental implant is a titanium post surgically placed in the jawbone to replace a missing tooth root, topped with a custom crown. At Grove Periodontists, most implants take 3 to 6 months from placement to final restoration and have a 95%+ success rate when placed by a board-certified periodontist." Then continue into the existing marketing narrative.

3. **New page: `/faq`** — consolidated FAQ hub with its own `FAQPage` schema, covering practice-level (not just procedure-level) questions:
   - "What does a periodontist do?"
   - "What's the difference between a periodontist and a dentist?"
   - "Do I need a referral to see a periodontist?"
   - "What insurance do you accept?"
   - "Where are your Richmond-area offices located?"
   - "Do you offer sedation dentistry?"
   - "What should I expect at my first periodontal consultation?"

4. **New page or section: `/results` (before/after gallery)** — neither site currently has one live; this is a multi-modal content gap (images with captions are citable and shareable, and this content type performs well for "what does gum grafting look like" / "dental implant before and after Richmond" style queries).

5. **Add FAQ schema + question-phrased H2s to the 2 location pages** (`/locations/richmond`, `/locations/midlothian`) — currently these carry only `MedicalClinic`/`OpeningHoursSpecification` schema, no FAQ. Add: "Where is Grove Periodontists located in Richmond, VA?", "What are your office hours?", "Is parking available?" — these are exactly the query shapes Google AI Overviews serves for "periodontist near me" local intent.

6. **Add `BlogPosting`/`Article` schema + author byline + `datePublished`/`dateModified`** to the 3 existing blog posts — currently they carry no article-level schema at all, which weakens both AI citation and Google's E-E-A-T reading of authored content.

### C. Schema / robots / llms.txt tasks

1. **Fix the domain mismatch (blocking, do first)** — pick the single production domain (recommend confirming with client whether it's `richmondperio.com` or the practice keeps `richmondperioonline.com`), then update in one pass:
   - `lib/constants.ts` → `SITE_URL`, `PRACTICE_EMAIL`
   - `app/layout.tsx` → `metadataBase`, `openGraph.url`, `alternates.canonical`
   - `app/sitemap.ts` → `BASE_URL`
   - `app/robots.ts` → `sitemap` value (must match `app/sitemap.ts` output domain exactly)
   - `app/team/[slug]/page.tsx`, `app/blog/[slug]/page.tsx` → hardcoded breadcrumb URLs
   - `next.config.ts` → image `hostname` allowlist if domain changes

2. **Remove the duplicate FAQPage schema** — delete the inline `<script>` block in `app/services/[slug]/page.tsx` (lines 468–485) and keep only the `<FAQSchema faqs={faqs} />` render inside `components/services/FAQAccordion.tsx`. One canonical FAQPage block per page.

3. **Fix `sameAs` entity mismatch** — either rebrand the linked Instagram/Facebook accounts to Grove Periodontists, or create new Grove-branded profiles and update `lib/schema.ts` `generateLocalBusinessSchema()`. Add Google Business Profile URL to `sameAs` once claimed under the new name.

4. **Create `/public/llms.txt`** — adapt directly from `lib/chatbot-knowledge.ts`, which already has 80% of the needed structured content (practice overview, locations/hours/phone, services list, doctor credentials). Structure per the llms.txt convention:
   ```
   # Grove Periodontists
   > Board-certified periodontal and dental implant surgery practice serving
   > Richmond and Midlothian, Virginia.

   ## Locations
   [Richmond office — address, phone, hours]
   [Midlothian office — address, phone, hours]

   ## Services
   [Link + 1-line description for each of the 6 procedure pages]

   ## Team
   [Link + credentials for each of the 4 doctors]

   ## FAQ
   [Link to /faq]
   ```
   This is low-effort since the source content already exists in the codebase.

5. **Add named crawler rules to `app/robots.ts`** (currently one wildcard rule) — make AI-search allow-listing explicit rather than implicit:
   ```ts
   rules: [
     { userAgent: ["GPTBot", "OAI-SearchBot", "ClaudeBot", "PerplexityBot"], allow: "/" },
     { userAgent: "*", allow: "/" },
   ]
   ```

6. **Add `datePublished`/`dateModified`** to `MedicalProcedure` and blog `Article` schema so freshness is machine-readable (currently absent from every new-site schema block).
